## Summary

Three additive pieces, built in this order, none of which edits `twin/` or the console:

1. **`voice/`**: mic -> silero VAD -> faster-whisper small (int8, CUDA) -> Qwen3-4B Q4_K_M on a llama.cpp server (streaming, budgeted thinking) -> sentence splitter -> Kokoro TTS, with an async orchestrator, an IDLE/LISTENING/THINKING/SPEAKING state machine, barge-in, a per-turn jsonl metrics log and a 20-turn latency report. Built in the user's four gated steps (stub loop < 500 ms first).
2. **`app_min.py` + `twinmin/`**: a second, minimal Gradio app on port 7881 with a persona picker and upload/build/activate, a voice panel, and a chatbox that shares one conversation and one LLM with the voice path and shows reasoning collapsed; thumbs and corrections feed a per-persona `feedback.jsonl`.
3. **`train/`**: per-persona QLoRA on the RTX 2070 from the persona's own files plus feedback (gold answers held out), exported to GGUF, served through `--lora-scaled`, gated by a before/after judge eval, retrained on demand from the UI while voice is stopped.

All three run in a new Python 3.12 conda env `twin-voice`; the console keeps the base env.

## Context

The project (`C:\Users\Adity\Personal_digital_twin`) is a local digital twin: a Gradio 6.27 console with eight tabs that answers as one person from `data/twin_profile.md` and a redacted interview transcript, using 13 local models on one RTX 2070 (8 GB). It is text only. The user wants the same twin spoken (mic in, twin voice out, conversational latency), plus a second, minimal UI where personas can be uploaded and chosen, chatted with (with a little visible thinking), and improved with a per-persona LoRA adapter. Everything stays offline at run time. The existing console, its endpoints and the demo run sheet must keep working unchanged.

Why now: the console proves the pipeline works; the voice layer and the minimal UI are what a client demo actually needs, and the LoRA step is the user's chosen answer to "the voice is wrong" (weights, not more prompt).

Module summaries:
- `audio_io.py`: `Mic` = `sounddevice.InputStream(16000, blocksize=512, float32)` on the WASAPI device (`pick_device`, `--list-devices`), callback stamps each block with `perf_counter()` into a `SimpleQueue`, async `frames()`. `Player` keeps one `OutputStream(24000, blocksize=480)` open all session; `enqueue(turn_id, audio)` into a lock-protected deque; the callback zero-fills on underrun and stamps `first_audio_ts[turn_id]` the first time it writes non-silent samples (this is the "first audio out" clock); `flush()` clears the deque so the next 20 ms block is silence (abort <= 20 ms, no stream restart); `drained(turn_id)` event.
- `vad.py`: `SileroGate` runs `load_silero_vad(onnx)` per 512-frame on CPU (~1 ms) with its own start/end logic (not `VADIterator`) so the threshold can depend on state: `feed(frame, ts, speaking) -> Start | End(ts, audio, silence_ms) | BargeIn(ts)`; pre-roll ring, utterance buffer capped at `max_utterance_s`; `BargeIn` only after `min_speech_ms` of consecutive frames above `threshold_speaking`; `End` when `end_silence_ms` of frames are below `threshold` (that instant is `vad_end_ts`).
- `stt.py`: `WhisperSTT.load()` imports torch first, then `WhisperModel(path, device="cuda", compute_type="int8_float16")`; `warmup()`; `transcribe(audio) -> SttResult(text, ms, no_speech_prob, avg_logprob)` with `beam_size=1, best_of=1, temperature=0, vad_filter=False, without_timestamps=True, condition_on_previous_text=False` (timer wraps `list(segments)`); text is "" under `min_chars`, on a `drop_phrases` hit, or past the probability thresholds. Blocking, run via `asyncio.to_thread`.
- `llm.py`: `LlamaServer.start()` probes `/health` and attaches when `attach_if_running` and `/props` reports the same model, else spawns `[server_exe, -m, model, --host, --port, -ngl 99, -c 4096, -np 1, -b 2048, -ub 512, -fa on, -ctk q8_0, -ctv q8_0, --cache-reuse 256, -t 4, --jinja, --reasoning-format auto, --reasoning-budget 256, --alias qwen3-4b, --slots, --metrics, --no-webui, (--lora <path> when set), *extra_args]` (stdout to `data/voice_llama.log`, `CREATE_NEW_PROCESS_GROUP`), polls `/health` until 200; `stop()` and `atexit`; `alive()`, `info()`. `LlamaClient.stream_chat(messages, *, thinking, max_tokens, temperature, turn_id) -> AsyncIterator[LlmEvent]` posts `/v1/chat/completions` via `httpx.AsyncClient.stream` with `{"model": alias, "stream": true, "stream_options": {"include_usage": true}, "max_tokens": reply_tokens + (reasoning_budget if thinking else 0), "chat_template_kwargs": {"enable_thinking": thinking}, **sampling}`, parses SSE into `Reasoning(text)` (from `delta.reasoning_content`), `Content(text)`, `Done(usage, timings, finish_reason)`; one turn lock so chat and voice serialise; a sync iterator wrapper for the UI. Audio task feeds the VAD with `speaking = (state is SPEAKING)`: `Start -> LISTENING`; `End -> THINKING`, `turn_id += 1`, spawn `turn_task`; `BargeIn -> cancel sequence -> LISTENING`. `turn_task`: STT in a thread; empty -> `IDLE` (`stt_empty`, metrics flagged, no prompt sent); bridge builds the messages (retrieval only under interview); stream: `Reasoning` keeps THINKING and counts; `Content` -> splitter -> TTS thread with the turn id -> `player.enqueue` only if the id is current; first `first_audio_ts` -> `THINKING -> SPEAKING` and closes the clock; `Done` -> postprocess, `Conversation.append`, audit, metrics line, print; `player.drained -> IDLE`. Degradation: TTS raising -> text mode for the rest of the turn; LLM error or empty content -> one retry with thinking off, else `IDLE` (`llm_empty`).
- `__main__.py`: `python -m voice [--stub] [--turns N] [--report] [--thinking on|off] [--condition ...] [--config PATH] [--no-barge-in] [--list-devices] [--yes] [--show-thinking] [--debug-slots]`; headphones warning (Enter unless `--yes`), GPU handshake, load, start or attach the server, warm up, log the steady-state VRAM proof line, run; `finally` stops the server it spawned. Exit codes 0 ok, 2 config, 3 GPU refused, 4 server unhealthy.
- `report.py`: `python -m voice.report --last 20 [--run ID] [--md docs\VOICE_LATENCY.md]`: run header, aggregate table (n / median / p90 / max per `_ms` field plus context tokens and VRAM max), per-turn table; `stt_empty`/`cancelled` rows listed but excluded, with the count and the pass/fail verdict against 900 ms.

**3. GPU handshake with the console.** At start `TwinBridge.free_console_gpu()` calls `twin.gpu.MANAGER.free_all()` (`gpu.py:114-132`), then polls NVML up to `wait_free_s` until used <= `max_used_mb_at_start` (300; `--max-gpu-mb` overrides like `demo_prep.ps1 -MaxGpuMiB`); above it, exit 3 with "run `scripts\free_gpu.ps1`, then retry". Why the console must be view-only while voice runs: `MANAGER` is per process; the console's heartbeat (240 s) re-warms `TAB_MODEL[active_tab]` (5.6 GB models) and `ensure()` cannot see a llama-server, so it would load beside the 4.5 GB voice stack and spill to the CPU. With `TWIN_NO_WARM=1` the console starts no heartbeat and no pre-warm, so both can run: console on Onboarding/Items/Eval (cached)/Status, voice holding the GPU. Status "Free GPU" is harmless to the voice stack. The interview condition is the one thing that puts a model into Ollama on purpose (nomic, ~0.5 GB, counted in the budget); the runtime falls back to persona with a warning if Ollama is down. On exit: stop the spawned server, drop the torch models, `torch.cuda.empty_cache()`; README "after the demo": `scripts\free_gpu.ps1` and `Get-Process llama-server -ErrorAction SilentlyContinue` must be empty.

**5. Thinking.** Flags `--reasoning-format auto --reasoning-budget 256 --jinja`; per request `chat_template_kwargs.enable_thinking` and `max_tokens = reply_tokens + 256` when enabled (otherwise the budget starves the reply, the same failure CLAUDE.md records for Ollama); sampling switches between the two tables. While `Reasoning` deltas arrive the state stays THINKING; they are counted (`thinking_tokens`) and timed (`llm_thinking_ms` = first reasoning delta to first content delta), never reach the splitter, never print unless `--show-thinking`, never enter the conversation window. `llm_first_token_ms` is the first delta of any kind; `llm_first_content_ms` the first content delta. Expected cost at 60-80 tok/s: up to 3.2-4.3 s for the full budget, 1.2-2.5 s for typical short thinking. Two runs go into `docs/VOICE_LATENCY.md`: `--thinking off` (acceptance, median < 900) and `--thinking on` (reported, with `llm_thinking_ms` and `thinking_tokens` columns), same 20 questions (listed in the report's appendix). Optional tunable `thinking.cue=false`: a pre-rendered short Kokoro clip played when reasoning starts (off by default; not prompt text).

**6. Barge-in.** Echo mitigation: headphones required (README and the `headphones_ack` prompt); while SPEAKING the gate uses `threshold_speaking=0.85` and `min_speech_ms=250` of consecutive speech frames; `cooldown_ms=300` after playback starts; the mic RMS during the first 500 ms of playback is logged once per session as `echo_rms_db` so a missing-headphones setup is visible. Cancellation sequence (`Orchestrator.cancel_turn(reason)`): (1) `turn_id += 1` (late chunks with the old id are dropped at the splitter->TTS hand-off and at `enqueue`); (2) `player.flush()` (silence within one 20 ms block; `barge_in_stop_ms` logged); (3) `turn_task.cancel()` and await it (unwinds `async for` inside `client.stream`, closing the socket so llama-server drops the slot); (4) splitter discarded; (5) pending TTS futures ignored (at most one chunk, ~100 ms of GPU); (6) old turn written with `cancelled=true`, audit `ok=false, extra.cancelled=true`, spoken part into the conversation; (7) the VAD pre-roll becomes the start of the new utterance, state LISTENING. Unit test `tests/test_voice_runtime_orchestrator.py::test_barge_in_cancels_playback_and_llm`: fake LLM yielding deltas with `await asyncio.sleep(0.01)` and recording `aclose()`, fake TTS returning 0.5 s of zeros per chunk, fake Player recording `enqueue`/`flush`, fake VAD script `[Start, End(audio), BargeIn at t+0.15 s, Start, End(audio2)]`; asserts `flush` once right after the first `enqueue`, `aclose` count 1, no `enqueue` with the old id after the flush, transition `SPEAKING -> LISTENING (barge_in)`, the second turn completes with `total_to_first_audio_ms`, two metrics lines (first `cancelled=true`). Plus `during_thinking=true` (`THINKING -> LISTENING (barge_in_thinking)`) and `enabled=false` (no barge-in). Live gate (Step 3): headphones on; ask for a long reply; speak one second into playback; pass when audio stops within 150 ms (`barge_in_stop_ms` + `min_speech_ms` printed), the new turn answers the interruption, no old audio resumes, `GET /slots` shows the old slot idle within 200 ms (`--debug-slots`); 5 of 5.

**10. Risks (ranked) and fallbacks:** (1) STT eats the budget on long utterances: trailing trim, `distil-small.en`/`base`, `int8_float16`, lower `max_utterance_s` for the acceptance run and say so. (2) Kokoro torch path fails on Windows (misaki/spaCy/espeak DLLs): `kokoro-onnx` + `onnxruntime` with the same `synth(text)` signature, a replacement not a layer. (3) Steady-state VRAM over 5,000: `n_ctx 3072`, then `tts.device="cpu"`, then whisper `base`. (4) Closing the stream does not cancel generation: `n_parallel=2`, `n_ctx=8192` (per-slot 4096, +300 MiB), `reply_tokens` 300 so an orphan ends within ~4 s. (5) False barge-ins from echo or breathing: headphones; `threshold_speaking` up to 0.9, `min_speech_ms` up to 400. (6) `-fa on` / q8_0 KV slow or unsupported on Turing: drop `-ctk/-ctv`, `flash_attn="auto"`, f16 KV at 4096 (580 MiB) still fits. (7) ctranslate2 cannot find cuBLAS/cuDNN: import order; `nvidia-cublas-cu12 nvidia-cudnn-cu12` plus `os.add_dll_directory`. (8) Console heartbeat loads a model mid-run: the handshake and the `TWIN_NO_WARM=1` rule. (9) Thinking starves the reply: `max_tokens` bump plus one no-think retry. (10) Old llama.cpp build mishandles `enable_thinking` or the budget: pinned tag; envcheck line 10. (11) Audio underruns while the GIL is busy: worker threads, 40 ms pre-buffer; `output_block=960` if clicks persist. (12) Interview prompt overflows `n_ctx`: the estimate refuses and names the fix. (13) 4B voice fidelity versus Stheno: section C; `postprocess_voice` per chunk keeps artifacts out of the audio.

### C. LoRA training (`train/`)

**Placement.** New top-level package `train/` (sibling of `twin/` and `voice/`). It imports `twin.profile`, `twin.transcript`, `twin.prompts`, `twin.pipelines.evals`, `twin.gpu`, `twin.audit`; nothing in `twin/` or `voice/` imports `train.trainer`/`train.convert` (the only modules touching torch/peft/bitsandbytes, imported lazily inside functions). Facts checked by the designer: Mara has 15 samples, 15 decisions, 4 highlights, 5 beliefs (one politics), 6 preferences, 2 routines, 3 life events, 20 Eval; the redacted transcript has T-001..T-038 in blocks 1-6 and T-039..T-060 in block 7; `build_voice_system(..., [], condition="persona")` is about 750-850 tokens for Mara (the 1,500 figure is the lint budget, not the actual size).

**1. Dataset builder** (every example = `{"id","source","messages": [system, (history...), user, assistant]}`, loss only on the final assistant message; Mara counts in brackets):
- Transcript turns outside `exclude_blocks` (`transcript.included_turns`): Q verbatim -> A verbatim; sentences containing `[...]` redaction placeholders dropped (`drop_placeholder_sentences=true`); the boundary deflection turn kept on purpose [38].
- Decisions: `"{situation} the options were {A} or {B}. what did you do, and why?"` -> `"{choice}. {why} {outcome}"` (only a period and spaces are template text) [15].
- Voice samples minus the first `n_prefix_samples=3` (already in the system prompt): one fixed neutral prompt `sample_prompt="text me back the way you'd actually type it, about anything"` -> sample verbatim [12].
- Interview highlights ("tell me about {x}") [4]; Beliefs minus `exclude_belief_topics=["Society and politics"]` [4]; Preferences / Routines / Life events with fixed topic questions [6/2/3]; Values, People, Goals with fixed generic questions [3].
- Feedback (`feedback.jsonl`): history (last 6 entries, system dropped and re-attached) + final user -> `corrected` text when present, else `reply` when `rating == "up"`; `down` without a correction is never trained on and lands in `manifest.rejected[]` for a later DPO/ORPO pass. Targets pass through `prompts.postprocess_voice`; empty -> dropped. Dedupe key sha256(messages + target). A feedback example whose final user message matches an Eval question (normalized equality or Jaccard of `lexical_words` > 0.8) is dropped (hard rule: the eval questions get typed in demos).
- Excluded by construction: Eval (never read except by the leak guard), block-7 turns, Self-ratings, Expert reflections, Changelog.
- System prompt: every example uses `prompts.build_voice_system(profile, digest, [], condition="persona")` byte-identical to serving's persona condition. Reasons: the adapter's job is voice, facts stay in retrieval; with CONTEXT the example's own chunk would be the top hit for its own question and the model learns verbatim copying; sequence length stays under `max_len=1536`. The train/serve gap under interview is bounded (same prefix, a CONTEXT block appended) and measured by the eval. Fallback behind `dataset.context="loo_retrieval"`: leave-one-out retrieval, k=3, `max_len=2048`, rank 8.
- Leak guard (`train/leak.py`, reuses `evals.lexical_words` and `evals.containment`): hard failures abort the build (any example from block 7 or Eval; a completion containing a gold answer as a normalized substring or the reverse; a prompt equal to an Eval question); soft rule drops and logs any completion with containment > 0.6 against any gold answer. Expected on Mara: drops `Interview/T-022` (Q-05, 0.63), `Decisions/D-15` (0.64), `Highlights/On money` (0.70), `On being told what to do` (0.67), `On close friends` (0.86), `Beliefs/Technology` (1.0), `Goals` (0.78); about 80 examples remain before feedback.
- Floors: `min_examples=40` and `min_completion_tokens=3000`; below them the job writes `state="insufficient_data"` and stops (`--allow-small` trains at rank 8, 4 epochs, gate decides). Split: 10% validation stratified by source, seeded, stored in the manifest, used for best-epoch selection.

**2. Training recipe** (`train/trainer.py` in the `_train_worker.py` subprocess):
- Base: `Qwen/Qwen3-4B` (the hybrid-thinking release the Q4_K_M GGUF was quantized from; NOT `-Base`, `-Instruct-2507`, `-Thinking-2507`, which share shapes and would load silently but wrong). About 8.1 GB bf16 safetensors: `hf download Qwen/Qwen3-4B --local-dir models\hf\Qwen3-4B --exclude "original/*"` once, then offline; also the converter's `--base`; revision sha recorded in the status file.
- Env pins (in `twin-voice`): `torch==2.7.1` cu126, `transformers==4.57.3`, `accelerate==1.12.0`, `peft==0.17.1`, `bitsandbytes>=0.47,<0.50` (Windows wheels bundling cuda126; verify with `python -m bitsandbytes`), `safetensors`, `jinja2`; no `datasets`, no `trl` (a 40-line completion-only collator).
- Loading: `BitsAndBytesConfig(load_in_4bit, nf4, double_quant, compute_dtype=float16)`, `torch_dtype=float16`, `attn_implementation="sdpa"` (flash-attn needs Ampere), `device_map={"":0}`, `prepare_model_for_kbit_training(use_gradient_checkpointing=True)` with `use_reentrant=False`.
- LoRA: r=16, alpha=32, dropout=0.05, targets `q_proj,k_proj,v_proj,o_proj,gate_proj,up_proj,down_proj` (~33M params), `bias="none"`, no DoRA, no rsLoRA, no `modules_to_save` (all break or mis-scale the GGUF converter).
- `max_len=1536` (examples over it dropped with a note, never truncated mid-answer); batch 1, `grad_accum=8`, `lr=1e-4`, cosine, warmup 5%, `epochs=3`, `max_grad_norm=1.0`, `fp16` AMP with GradScaler (LoRA weights fp32), `adamw_torch` (`paged_adamw_8bit` on OOM), `save_strategy="epoch"`, best epoch by val loss, `seed=1234`, `dataloader_num_workers=0`.
- Template: prompt = `apply_chat_template(messages[:-1], tokenize=False, add_generation_prompt=True, enable_thinking=False)` (ends `<|im_start|>assistant\n<think>\n\n</think>\n\n`); completion = `answer + "<|im_end|>\n"`; tokenize both with `add_special_tokens=False`; labels mask the prompt and the trailing `\n`. A test asserts prompt + completion equals the full-conversation render and the concatenated ids equal the full text's ids. Thinking: train with the empty think block present and masked, so the non-thinking generation prompt matches exactly and no gradient touches thinking, preserving budgeted thinking at inference. Never synthesize reasoning traces.
- VRAM (voice stopped): NF4 weights ~2.7 GB + LoRA/opt ~0.5 + checkpointed activations ~0.6 + logits at 1536 x 151,936 up to ~2.3 transient + context ~0.6 = peak ~6.0-6.8 GB at 1536 (~5.3-5.8 at 1024); `train.vram_limit_mib=7600` aborts above; OOM fallback chain applied one step at a time with a restart: `max_len 1024` -> rank 8 -> `paged_adamw_8bit` -> drop the two longest examples; `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`.
- Wall time for ~100 examples x 3 epochs (~330k tokens incl. masked prefix): load 1-2 min, training at 250-450 tok/s = 12-25 min; budget 15-30 min. A logger callback writes `tokens/step`, `s/step`, loss, lr, `max_memory_allocated` per `on_log` and an `eta_s` into the status after 10 steps.

**3. Export and serving.** No merge (the Q4_K_M base stays). Converter: read the server tag from `llama-server --version`, fetch `https://github.com/ggml-org/llama.cpp/archive/refs/tags/<tag>.zip` into `tools/llama.cpp-src/<tag>/` (`convert.resolve_llama_cpp_src`), install `requirements/requirements-convert_lora_to_gguf.txt` with `--no-deps` for torch. Command: `python tools\llama.cpp-src\<tag>\convert_lora_to_gguf.py --base models\hf\Qwen3-4B --outtype f16 --outfile personas\<slug>\build\lora-vN.gguf personas\<slug>\build\lora-vN` (~66 MB). `convert.verify_gguf` reads the header with `gguf-py` (`general.architecture == "qwen3"`, `adapter.type == "lora"`, `adapter.lora.alpha == 32`, tensor count 7 x 36 x 2). Switch = (a) restart llama-server with `--lora-scaled <gguf>:<scale>` for the active persona (chosen: new files need a restart anyway, voice is already stopped, one adapter per process keeps VRAM and the prompt cache simple); (b) pre-loading several adapters and switching by scale stays available through `serve.lora_args(personas)` (scale 0 for inactive) and the per-request `lora` field. `personas/<slug>/build/lora_status.json` (atomic write like `evals.save_results`): `{persona, state: idle|building|training|converting|evaluating|activating|done|failed|insufficient_data, run_id, step, progress, eta_s, message, error, active_version, active_gguf, scale, candidate_version, versions: [{version, trained_at, examples, epochs, train_loss, val_loss, vram_peak_mib, train_s, eval: {base_overall, adapter_overall, delta, ci95}, gate_passed, activated}], profile_sha, transcript_sha, digest_sha, base_hf_revision, llama_cpp_tag, feedback_count, feedback_since_last_train, retrain_suggested, updated}`. The UI reads it (`train.status.read(slug)`) and passes the active gguf into `voice.llm.LlamaServer(lora_path=...)`; `voice/` never imports `train`.

**4. Evaluation** (`train/evaluate.py`, `train/llama_client.py`): base (adapter at scale 0) vs adapter (scale 1.0) on the 20 `profile.eval` questions, same sampling (`eval.temperature=0.7, top_p=0.8, top_k=20, min_p=0`, `max_tokens=300`), condition default `["interview"]` (the serving condition of chat), `eval.thinking="off"` (`chat_template_kwargs.enable_thinking=false`; residual `<think>` stripped). GPU sequencing: `MANAGER.free_all()`; precompute interview retrieval with the persona's nomic index (`evals.precompute_retrieval`); `free_all()` and wait < 300 MiB; start llama-server with `--lora-scaled <gguf>:0.0`; 20 base + 20 adapter generations (per-request `lora` scale; each writes `audit.record("train", ...)` with no text in `extra`); stop the server; judges `llama31` then `qwen25` on Ollama via `evals.judge_reply` (judge-outer, existing `JUDGE_SYSTEM`/`JUDGE_SCHEMA`, temperature 0); `free_all()`. Base answers cached per (profile sha, condition, thinking). Statistics: per judge, per-question difference adapter minus base, paired bootstrap (2000 resamples, seed 0) on the mean, pooled over judges; written to `build/lora-vN.eval.json` and `build/lora_eval.json` with per-question replies, means per judge, `diff` (pooled overall, ci95, per judge, per key), `sanity` (`_ACTION_RE` hits, name-prefix lines, `_AI_TAIL_RE` hits, empty replies, `<think>` leaks, parroting fraction = adapter replies with containment > 0.8 against any transcript answer), `gate`; `evaluate.table_rows()` for the UI. Gate (point estimates with tolerances, since n=20 integer scores give a CI of about +/-0.4): pooled overall delta >= 0.0, factual drop <= 0.25, artifacts drop <= 0.10, artifact count not increased, parroting <= 0.3. A regressing adapter is never activated; the previous active version stays.

**5. The job** (`train/job.py`, CLI `python -m train --persona <slug> [--epochs N] [--eval|--no-eval] [--activate|--no-activate] [--restart|--no-restart] [--only build|train|convert|eval|activate] [--version N] [--resume <run_id>|last] [--allow-small] [--eval-n 10] [--eval-conditions ...] [--status] [--dry-run]`): (1) preflight: parse profile/transcript; redacted transcript present; `build/digest.md` sha == profile sha; the voice server not running and its port closed; `gpu_guard.assert_gpu_free(300)` via pynvml (names the offending processes); base HF dir and converter source present. (2) build dataset + leak guard -> `dataset-vN.jsonl` + manifest (counts by source, dropped, token histogram, input shas, split); `insufficient_data` stop. (3) train in the worker subprocess with `resume_from_checkpoint`, the OOM chain on CUDA OOM. (4) convert + verify. (5) eval when `--eval` (an unevaluated version needs `--activate --force`). (6) write status, activate when the gate passed, restart the server only from the CLI (`--restart` default there; the UI passes `--no-restart` because it owns the server: stop -> `train.launcher.spawn_retrain` -> poll `train.status` -> start). `server_control` protocol (`is_running()`, `stop()`, `start(extra_args)`) supplied by the caller. Logging: `runs/<run_id>/log.jsonl` one line per event; `--resume last` skips done steps. Auto retrain: `[retrain] auto=false, after_new_feedback=20, min_interval_hours=24`; `status.should_auto_retrain(slug)` only sets `retrain_suggested: true` (training needs the voice stack stopped, so the UI nudges; never runs by itself).

**6. Config** `train/config.toml` (training tunables have their own lifecycle); shared serving values (server exe, base GGUF, host/port, server args, samplers, reasoning budget) are read from `voice/config.toml`'s `[llm]` and `[llm.sampling_nothink]` sections and never duplicated. Defaults: `[paths] personas_dir="personas" base_hf_dir="models/hf/Qwen3-4B" llama_cpp_src="tools/llama.cpp-src" python="" hf_offline=true`; `[dataset] context="none" n_prefix_samples=3 drop_placeholder_sentences=true include_sections=[decisions,samples,highlights,beliefs,preferences,routines,life_events,values,people,goals] exclude_belief_topics=["Society and politics"] sample_prompt=... sample_repeat=1 max_history_turns=6 feedback_accept=["up","correct"] feedback_require_consistent=false val_fraction=0.1 seed=1234 min_examples=40 min_completion_tokens=3000`; `[leak] threshold=0.6 hard_fail_on_verbatim=true`; `[train] rank=16 alpha=32 dropout=0.05 target_modules=[...] max_len=1536 epochs=3 lr=1e-4 warmup_ratio=0.05 scheduler="cosine" batch_size=1 grad_accum=8 optimizer="adamw_torch" fp16=true compute_dtype="float16" gradient_checkpointing=true attn="sdpa" save_strategy="epoch" select_best_by="val_loss" max_grad_norm=1.0 weight_decay=0.0 seed=1234 vram_limit_mib=7600`; `[train.oom_fallback] max_len=1024 rank=8 optimizer="paged_adamw_8bit" drop_longest=2`; `[convert] outtype="f16"`; `[eval] enabled=true n_questions=20 conditions=["interview"] judges=["llama31","qwen25"] thinking="off" reasoning_budget=256 temperature=0.7 top_p=0.8 top_k=20 min_p=0.0 max_tokens=300 seed=7 bootstrap_resamples=2000 cache_base_answers=true`; `[eval.gate] min_gain_overall=0.0 max_factual_drop=0.25 max_artifact_drop=0.10 max_artifact_count_increase=0 max_parroting_fraction=0.3`; `[serve] switch="restart" scale=1.0 restart_after_train=true`; `[retrain] auto=false after_new_feedback=20 min_interval_hours=24`; `[gpu] max_used_mib_before_train=300 free_wait_s=30`.

**7. Tests** (offline; torch-dependent ones `importorskip`): `test_train_dataset.py` (per-source counts on the real Mara files 38/15/12/4/4/6/2/3/3; no block-7 turn; every system message byte-equal to `build_voice_system(profile, digest, [], "persona")`; samples 1-3 never a completion; placeholder sentence removed; dedupe; deterministic split; manifest fields), `test_train_leak.py` (70% containment dropped with reason; verbatim gold -> hard error; block-7 turn with `exclude_blocks: []` still excluded; Mara's seven dropped ids), `test_train_template.py` (vendored Qwen3 chat template rendered with jinja2: prompt ends with the empty think block, prompt + completion equals the full render, earlier assistant turns render without think blocks; a tiny `PreTrainedTokenizerFast` checks the label mask and boundary tokenization), `test_train_feedback.py` (malformed lines skipped, up/down/correct policy, history truncated to 6, eval-question drop, dedupe, `count_since`), `test_train_status.py`/`test_train_serve.py` (atomic write, defaults, versions, `should_auto_retrain`, `lora_args` formatting), `test_train_eval.py` (`LlamaServer.chat` against `httpx.MockTransport` asserting the `lora` field, `chat_template_kwargs`, sampler; `FakeOllama` judges in the style of `tests/test_evals.py`; deterministic `bootstrap_ci`; gate decisions; `table_rows` shape; eval json schema), `test_train_cli.py` (step functions monkeypatched: ordering, `state.json`, `--only`, `--resume`, `insufficient_data`, preflight refusal when a fake pynvml reports 4,500 MiB), `test_train_imports.py` (light modules leave torch out of `sys.modules`), a mocked trainer on a 2-layer random `Qwen3Config` on CPU for one step (labels masked, adapter dir written, loss line logged). Live check: `python -m train --persona mara --epochs 1 --eval` passes when final train loss <= 0.8 x first-step loss and val loss not rising, `vram_peak_mib < 7600`, `lora-v1.gguf` verified and listed by `GET /lora-adapters`, `lora_eval.json` has 20 x 2 judges x 2 candidates with no error cells, artifacts not increased, status `done`.

**8. Risks (ranked) and fallbacks:** (1) bitsandbytes cannot load its CUDA library on Windows: match the wheel's bundled CUDA to torch's (cu126), `BNB_CUDA_VERSION=126`, `python -m bitsandbytes`; if unusable, `train.quant="quanto"|"hqq"` (pure-PyTorch int4, peft-compatible, Turing-safe); last resort fp16 base with CPU offload; the cu118 torch line is not a fallback. (2) Turing fp16 overflow: abort on NaN; halve lr; `compute_dtype="float32"` + `fp16=false` (2-3x slower). (3) Converter vs Qwen3: supported (`Qwen3ForCausalLM` mapping), but it rejects `modules_to_save`, DoRA, `lora_bias` and mis-scales rsLoRA (none used); pin the source zip to the server tag. (4) Server rejects the adapter: `verify_gguf` first; status records the base revision; `gguf_dump.py`; retrain with default targets. (5) Overfitting on ~80 examples: dropout, 3 epochs, best epoch by val loss, the parroting probe and the gate. (6) NF4-trained delta vs Q4_K_M serving base: measured by the eval; `loo_retrieval` if it helps under persona but not interview; attribute with a Q8_0 base once if the gap persists; no merge unless the user changes their mind. (7) Time (25-50 min per retrain with voice down): `--epochs 2`, `--eval-n 10`, cached base answers, ETA after 10 steps. (8) Coupling: per-persona digest and nomic index must exist before training (sha checks refuse otherwise); the UI spawns the job with the 3.12 python. (9) Windows: `num_workers=0`, no `torch.compile`, short `build/` names, antivirus slowing the 8 GB load, `--local-dir` to avoid symlinks. (10) Feedback contamination: thumbs-up on hallucinated facts teaches facts; optional `feedback_require_consistent` when the UI records the checker verdict; the eval-question drop protects the held-out set.

### Cross-design reconciliation (final API)

- Package names: `voice/` (A), `twinmin/` + `app_min.py` (B), `train/` (C). B's "`lora.train(...)`" is `train.launcher.spawn_retrain(slug, ...)` plus `train.status.read(slug)`; B's `LlamaServer(lora_path=...)` gets its path from `train.status.read(slug)["active_gguf"]` (the UI passes it; `voice/` never imports `train`).
- Feedback row (B writes, C reads): `ts, persona, profile_sha, turn_id, source, condition, think, messages (system + window + user), chunk_ids, reasoning, reply, rating (up|down|correct), corrected, adapter_version, model`; `train.feedback` drops any system message and re-attaches the persona prefix, and treats `rating == "correct"` with `corrected` as the target. C's optional `checker` field is absent until the UI records a checker verdict.
- Persona layout: C reads `build/interview_transcript.redacted.md`, `build/digest.md`, `build/index_nomic.npz` from B's registry; `mara` resolves to `personas/mara/build/` (B's startup snapshot) else the `data/` example files.
- Shared config: `train.config.load()` reads `voice/config.toml` `[llm]` and `[llm.sampling_nothink]` for the server command and samplers; the `twin-voice` python is `[paths].python` when set, else `sys.executable`.
- Conditions: voice `persona` (latency), chat and eval `interview` (grounded), all through `TwinBridge.build_messages(..., condition=)`.
- Context: `context.max_turns=6` pairs for voice and chat via `Conversation.window()`.
