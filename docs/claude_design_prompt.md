# Claude Design brief: the Digital Twin console

How to use: open claude.ai/design, upload the six current screenshots from `scripts\dev\shot_*.png` (the app as it is today: default dark Gradio, unstyled), then paste everything inside the fenced block below as the first message. When the canvas looks right, export as **standalone HTML** and as a **handoff bundle to Claude Code**, and save them under `docs\design\` (`docs\design\tokens.md`, `docs\design\screens\`). `docs\PLAN3_UI.md` turns that into the real app.

Revision 2 (2026-09-14): folded in the Anthropic `frontend-design` skill (anti-default rules, two-pass process, copy rules), the `redesign-existing-projects` audit (one accent, one grey family, one radius rule, tinted shadows, full state coverage) and Vercel's Web Interface Guidelines (focus, labels, tabular numerals, dark-mode `color-scheme`, reduced motion, loading text). The brief no longer prescribes an accent hue or fonts; it asks Claude Design to derive them from the subject and to justify them.

````
Desktop web app prototype, 8 screens, for one person demoing a local "digital twin" to friends and reviewers on their own laptop. The twin is a small language model that answers as the owner, in the owner's texting voice, predicts the owner's decisions, runs tools, reacts to images, and grades itself against the owner's real answers. Everything runs on the laptop's own GPU, so the interface must make "which model is on the GPU right now" visible on every screen. The attached screenshots are the current unstyled version: same information, same controls, no visual design.

SUBJECT AND TONE: this is a private instrument for one person, not a SaaS product and not a chatbot. It should feel like a well-made personal console: calm, precise, a little warm because it is about a person, confident because it reports measurements. Medium density: a reviewer must read a verdict or a table in one glance. Light-first with a complete dark variant.

PROCESS (do this in two passes): first, before any screen, write a compact design plan: a palette of 4 to 6 named hex values grounded in this subject, one or two typeface families with roles (say why each fits a personal console; Inter, Roboto, Arial and Helvetica only if you can argue for them), a type scale, a layout concept with an ASCII wireframe of the global frame and of the Ask screen, and three principles. Then check that plan against the anti-default list below and change anything that reads as the generic answer. Only then produce the screens. Spend boldness in one place: the persona header or the verdict card is the memorable element; everything else stays quiet.

ANTI-DEFAULT LIST (do not use any of these unless I ask): a warm cream background with a serif display and a terracotta or clay accent; a near-black background with one acid-green or vermilion accent; broadsheet hairline rules and zero border-radius everywhere; the SaaS card kit (every block an identical rounded card with the same grey shadow); tracked-out ALL-CAPS eyebrow labels above headings; meta strings joined with middle dots; labels built as "WORD — fragment"; tinted near-black standing in for black; a monospace face for small data labels; arrows appended to link or button text; purple or blue "AI" gradients; glassmorphism, mesh gradients, noise overlays; illustrations or decorative icons; scroll-triggered entrance animations. Positive rules instead: one accent color only, saturation under 80 percent, used consistently on every screen; one grey family (warm or cool, not both); one corner-radius rule stated explicitly (for example buttons 8, inputs 8, panels 12); shadows tinted to the background hue and used only where elevation means hierarchy; structure carries information (borders, dividers and numbering only where the content is really a sequence); tables and metrics use tabular numerals, and monospace appears only inside the trace panels where the content is actually code (tool arguments, JSON, chunk ids).

HARD CONSTRAINT: this will be implemented in Gradio 6, so every screen must be buildable from these building blocks only, stacked vertically or in rows and columns with simple width ratios: text and number inputs, multi-line text areas, buttons (primary, secondary, stop), sliders, checkboxes, dropdowns, a chat transcript with streaming bubbles and avatars, markdown blocks, JSON viewer, simple data tables, bar and line charts, image upload with drag and drop, collapsible accordions, tabs, a collapsible left sidebar, a step-by-step walkthrough, progress bars, status labels. No modals, no drawers, no absolute positioning, no drag-to-reorder, no custom animations beyond hover, focus and 200 to 300 ms state transitions that answer a user action. Max content width 1440 px; the Ask screen must also work at 400 px wide. Styling is applied through a theme (primary, secondary and neutral color scales 50 to 950, spacing, radius and text-size scales, two Google Fonts, about 200 named variables for backgrounds, borders, shadows, buttons, inputs, tables) plus a small custom CSS file, so give every color, size and font as explicit tokens.

QUALITY FLOOR (design it in, do not mention it): visible keyboard focus on every control; body text contrast at least 4.5:1 in both modes; every form control has a visible label; touch targets at least 44 px; the dark variant sets color-scheme dark so native selects and scrollbars match; reduced-motion users get no motion; loading text ends with an ellipsis character; errors are inline, say what happened and how to fix it, and never apologise; empty states tell the person what to do next. Copy: sentence case, active voice, plain verbs; keep every label and button text exactly as in the screenshots where it exists; invent nothing about the owner.

GLOBAL FRAME (every screen): a persona header with the twin's first name, an initial-letter avatar, the profile source and freshness, and a warning line when the real profile is missing. A persistent status strip (top or in the left sidebar) showing: GPU memory used of 8 GB, the model loaded on server A (LM Studio) and on server B (Ollama), the active tab, and a heartbeat indicator; states: idle, loading a model (cold start about 6 seconds), ready, busy. Navigation across 8 tabs: Ask, Decide, Act, See, Items, Eval, Status, and a first-run Onboarding.

SCREENS
1. Ask: chat transcript (streamed reply bubbles, owner's messages right), composer with Send and Clear, a control row: temperature slider (0.5 to 1.4), toggle "Q8 high-precision voice (slow)", toggle "Consistency check", dropdown "Condition: demographic / persona / interview". Under the transcript: a consistency badge (consistent or inconsistent with counts of unsupported claims and contradictions), a hint line ("this looks like a tool request, try Act"), and a collapsible Trace showing router intent, rewritten query, five retrieved chunk ids with scores, voice model, timings. Show the streaming state and the empty state.
2. Decide: situation text area; primary button "B1: Would I do it?"; two option fields A and B with "B2: A or B?"; a result card with a big verdict (YES/NO or A/B), a confidence meter 0 to 1, a reasons list, cited decisions as chips (D-01 plus title), "what would change my mind" or "tradeoff", and a footer with model name, milliseconds, chunks used; a raw-JSON accordion; a secondary button "Say it in my voice" that renders a quote card in the twin's voice. Show the loading state (model swap in progress).
3. Act: request field with placeholder "What time is it and what's 17% of 240?", Run button, answer panel, a step trace (each step: tool name, arguments, result), and "Polish with Stheno" producing a polished text panel.
4. See: image drop zone left, right column with "Description (vision model)" and "Reaction (in my voice)", a Look button, a trace line with timings; empty and loading states.
5. Items (self-report and scoring): a form of survey items grouped by instrument (Likert 1 to 5 rows, numeric allocation rows for four economic games, open questions), a date stamp and Save; a "Run twin" control with a condition dropdown and progress; a scoring table per instrument and condition with raw metrics and a normalized column that shows "ceiling pending" until a retest exists.
6. Eval: a note line about judges and whether the cloud judge is enabled (checkbox); "Voice bake-off" table (candidate, replies, factual, voice, artifacts, overall, consistent, overall by judge) with a small bar chart of overall per candidate; "Retrieval bake-off" table (index, recall@1/3/5, MRR, embed ms); buttons Refresh, Re-run voice bake-off (about 6 minutes, with progress), Re-run retrieval; a "Live: one candidate x one question" row with two dropdowns and a JSON result.
7. Status: model-and-job table (14 rows: key, server name, runtime, VRAM class, state loaded/on disk/no key, job), live server panels (Ollama loaded models with GPU percent and context, LM Studio models with state, nvidia-smi line), profile and index freshness, digest info, a telemetry table (last 30 calls: time, tab, model, load ms, tokens, tok/s, wall ms, ok) with a line chart of tokens per second, an audit tail, and buttons Free GPU, Warm current tab, Refresh, Rebuild index and digest, Rebuild digest.
8. Onboarding (first run, profile missing): a 4-step walkthrough: run the interview prompt, save the profile and transcript, rebuild the index, answer the self-report items; each step with a status check and a copyable command.

DELIVERABLES: (a) the design plan from pass one, with the anti-default check and what you changed; (b) a design-token sheet as a table: color scales for primary, secondary and neutral in light and dark (hex), semantic colors for success, warning, error, info, the two fonts with fallbacks and the reason for each, the type scale, spacing scale, radius rule, shadow levels, plus a "default_theme: light" line; (c) the 8 screens at 1440 px in light mode, the Ask and Status screens also in dark mode, and Ask at 400 px; (d) the states listed above (empty, streaming, loading a model, inline error, ceiling pending); (e) a one-page component sheet showing the styled version of every building block in the hard constraint, including focus and disabled states, so the implementer can map them one to one. Ask me clarifying questions only after producing the first version.
````
